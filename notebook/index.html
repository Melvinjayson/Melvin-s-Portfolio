01 / Method, not decoration

The visual should explain the system.

I am interested in visual ideas that are useful because of what they reveal. A change of state, an uncertain answer, a human approval, an interrupted workflow—these are not just technical events. They change what a person understands and can do next.

01 / Observe

Start with the task

Understand the person, the decision and the information that matters before choosing a visual form.

02 / Model

Make behaviour visible

Describe the system's states, transitions, constraints and recovery paths. Work out which should be visible to users.

03 / Prototype

Test the explanation

Build something interactive enough to learn from. A prototype can show how a concept behaves, even when it does not prove real-world performance.

02 / Interactive visual tokens

An icon grammar for invisible processes.

Traditional icon libraries tend to depict objects. Intelligent products also need ways to communicate things people cannot see: inference, uncertainty, delay, verification and handoff. This is a small, original design exercise, not a published product design system. Change a symbol and its tokens to see how a visual language might begin.

This interactive example demonstrates a possible visual language. The icons are not claims of validated user comprehension, measured confidence, or production deployment.

Why these five metaphors?

Inference hints at transformation from one signal to another; confidence represents a supported judgement, not certainty; latency represents a waiting period; handoff shows a change in responsibility; verification represents a reviewable checkpoint. Each metaphor would require user testing before use in a consequential interface.

Where do engineering decisions appear?

The interface uses a single SVG geometry definition per concept and separates those definitions from presentation tokens. The size, stroke weight and colour variants are controls rather than separate illustrations. That makes the exercise repeatable and easy to extend.

What remains unproven?

Recognition at 16–24 px, cultural interpretations, visual accessibility, semantic clarity across contexts and the ability of the icon to represent complex model behaviour. These are research questions, not assumed successes.

03 / Interactive 3D experiment

Dexterity Lab: making movement inspectable.

A controlled experiment in procedural motion and interface design. Instead of only watching an animation, a viewer can change tasks, scrub through time, jump to operations and inspect what the replay is showing.

Three.js / Procedural replay

Not a physics simulation. A way to ask better questions.

The current prototype demonstrates scripted Jenga, cube and cup sequences. It provides timeline controls, camera presets and object selection. Its geometric hands are simplified, and the force and stability numbers are illustrative—not measured physical data.

My design interest here is in how interfaces make complex movement visible: which object is active, what state an operation is in, and what information a viewer would need to understand or question a replay.

Explore the interactive prototype ↗
What's actually implemented?

Procedural object geometry, three operation modes, selectable task steps, playback, scrubbing, camera views and simple telemetry demonstrations. This does not use a validated robotic-hand model, collision solver or recorded kinematic dataset.

What would make it a serious robotics visualisation?

Verified joint definitions, a real articulated model, collision and grasp constraints, physically grounded datasets, calibrated time series, and tests that compare replay with known motion. The interface should keep kinematic observations separate from simulated forces.

What am I learning?

The value of an interactive prototype is not the render alone. It is the connection between what a user sees, the state of the system and the evidence available to explain it.

From a diagram to a working product.

My independent product work is another place where research and implementation meet. I work on interfaces, but also on the structure beneath them: data, permissions, workflow state, system boundaries and the questions a product must answer before it deserves to scale.

What can a person trust?
